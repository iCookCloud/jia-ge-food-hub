# 询价聊天系统重构方案

## 问题分析

### 当前架构的混乱情况

1. **两套聊天系统并存**
   - `chat_negotiations` 表：专门用于价格协商，字段复杂，包含价格提案逻辑
   - `user_messages` 表：通用消息系统，支持附件和已读状态
   - 两套系统功能重叠，维护成本高

2. **聊天与报价系统职责混乱**
   - `order_list_quotations` 表：用于货单报价业务，与聊天无关
   - `quotations` 表：旧报价系统，在聊天协商中被错误引用
   - 聊天功能错误地依赖报价表数据

3. **业务逻辑过度耦合**
   - 聊天功能与价格协商功能强耦合
   - 引入了不必要的确认流程、协商轮次等复杂概念
   - 违背了"询价就是聊天"的简单需求

4. **代码问题**
   - `ProductDetailPage.tsx:101` 询价按钮直接跳转 `/negotiations`，没有传递商品信息
   - `chatNegotiationService.ts` 中大量复杂的业务逻辑，与简单聊天需求不符
   - 多个服务文件职责重叠：`messageService.ts`、`chatNegotiationService.ts`

## 重构方案

### 核心设计原则

**询价 = 用户间聊天 + 货单引用功能**

### 1. 统一聊天系统

**使用 `user_messages` 作为唯一聊天表**
```sql
-- 保留 user_messages 表，暂不删除 chat_negotiations 表（等测试完毕后删除）
-- user_messages 表已有 referenced_order_list_id 字段
-- 添加货单卡片信息字段
ALTER TABLE user_messages ADD COLUMN referenced_list_summary JSONB;
```

**字段说明：**
- `referenced_order_list_id`：引用的货单ID（已存在，可为空）
- `referenced_list_summary`：货单卡片简要信息（JSONB格式）
- `quotation_id`：保留，用于关联具体的报价上下文（可为空）
- `message_type`：消息类型，支持 'text'、'product_list_reference' 等

**货单卡片信息结构（基于现有 OrderListSelector 卡片设计）：**
```json
{
  "name": "货单名称",
  "total_amount": 50000,
  "status": "shared",
  "created_at": "2024-01-01T00:00:00Z",
  "description": "货单简要描述",
  "delivery_location": "配送地址",
  "item_count": 15,
  "special_requirements": "特殊要求"
}
```

### 2. 简化聊天服务

**统一聊天服务 `chatService.ts`**
```typescript
export interface ChatMessage {
  id: string;
  sender_id: string;
  receiver_id: string;
  content: string;
  message_type: 'text' | 'product_list_reference';
  referenced_product_list_id?: string;
  quotation_id?: string;
  attachments?: any;
  is_read: boolean;
  created_at: string;
  sender_profile?: Profile;
  referenced_product_list?: ProductList; // 当引用货单时加载
}

export const chatService = {
  // 获取与特定用户的聊天记录
  getChatMessages(receiverId: string): Promise<ChatMessage[]>
  
  // 发送文本消息
  sendTextMessage(receiverId: string, content: string): Promise<ChatMessage>
  
  // 发送货单引用消息（包含卡片信息）
  sendProductListReference(
    receiverId: string, 
    productListId: string, 
    listSummary: ProductListSummary,
    message?: string
  ): Promise<ChatMessage>
  
  // 获取用户的聊天会话列表
  getChatSessions(): Promise<ChatSession[]>
  
  // 订阅实时消息
  subscribeToChatMessages(receiverId: string, callback: Function): RealtimeChannel
}
```

### 3. 页面结构重构

**重构范围说明**
- **只重构**: `/quotations` 聊天页面和商品询价功能
- **不涉及**: `/negotiations` 页面（属于独立的业务流程，后期可能单独处理）
- **目标**: 商品询价跳转到聊天页面，与协商流程完全分离

**商品相关询价跳转（需要修改的地方）**
```typescript
// ProductDetailPage.tsx 和 ProductCard.tsx
const handleInquiry = () => {
  if (!user || !product) {
    toast.error("请先登录");
    return;
  }
  
  // 跳转到与商品上传者的聊天页面，携带商品上下文
  const uploaderId = product.user_id; // 商品上传者ID
  const productId = product.id;
  navigate(`/quotations?to=${uploaderId}&product=${productId}`);
};
```

**订单协商入口（完全不涉及此次重构）**
```typescript
// OrdersPage.tsx - 保持不变，属于独立业务流程
<Link to="/negotiations">查看协商</Link>
```

**重构边界说明**
- 此次重构**只处理商品询价功能**
- `/negotiations` 页面及其相关逻辑**完全不动**
- 两套系统完全分离，互不影响

**QuotationsPage 扩展功能**
- 检测 `to` 参数：直接进入与指定用户的聊天
- 检测 `product` 参数：自动预填充商品询价消息
- 预填充模板：`"您好，我对您的 [商品名称] 感兴趣，请问..."`

### 4. 删除不必要的复杂功能

**移除以下概念：**
- 价格协商轮次
- 买家/供应商确认状态
- 价格提案状态
- 协商会话的复杂状态管理

**保留核心功能：**
- 用户间聊天
- 货单引用（点击查看详情）
- 消息已读状态
- 实时消息同步

### 5. 数据库表清理

**保留表：**
- `user_messages` - 主聊天表
- `profiles` - 用户信息
- `product_lists` - 货单信息（支持引用）

**暂不删除表（等测试完毕后操作）：**
- `chat_negotiations` - 协商表（仅在 `/negotiations` 业务中使用，不涉及此次重构）
- `quotation_conversations` - 报价对话表（如果存在）

**明确表职责：**
- `order_list_quotations` - 货单报价业务专用，与聊天无关
- `quotations` - 在协商业务中使用，与此次重构无关
- `user_messages` - 此次重构的目标聊天表

## 实现步骤

### 第一阶段：数据库扩展
1. 为 `user_messages` 表添加 `referenced_list_summary` JSONB 字段
2. 保留现有 `referenced_order_list_id` 字段
3. 暂不删除 `chat_negotiations` 表（等测试完毕后处理）

### 第二阶段：服务层重构
1. 暂不删除 `chatNegotiationService.ts`（保留作为参考）
2. 重构 `messageService.ts` 为 `chatService.ts`
3. 简化API接口，支持货单卡片信息

### 第三阶段：前端重构
1. 重构 `QuotationsPage` 支持 `?to={userId}&product={productId}` 参数
2. **不涉及 `NegotiationPage`**（属于独立业务流程）
3. 保留现有 `OrderListSelector` 弹框组件
4. 创建聊天内货单卡片组件（复用 `OrderListSelector` 的卡片设计，但更紧凑）
5. 修改商品页面的询价跳转逻辑：`ProductDetailPage.tsx` 和 `ProductCard.tsx`

### 第四阶段：功能完善
1. 实现货单引用时自动填充 `referenced_list_summary` 字段
2. 聊天内货单卡片点击查看详情功能
3. 保留现有弹框选择货单功能，适配新的消息表结构

## 预期效果

**简化后的用户体验：**
1. 用户在商品页面点击"咨询询价" → 直接进入与商品上传者的聊天页面
2. 聊天中可以引用货单，点击查看详情
3. 纯聊天体验，没有复杂的价格协商流程
4. 所有业务沟通通过聊天完成，由用户自主决定

**技术收益：**
- 代码量减少约50%
- 维护成本降低
- 架构清晰，单一职责
- 更好的扩展性

## 风险评估

**低风险：**
- 现有聊天数据可以完整迁移
- 用户体验更加简化直观

**需要注意：**
- 确保数据迁移过程中不丢失历史聊天记录
- 给用户明确的功能变更说明
